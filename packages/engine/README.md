# @number-island/engine

The pure TypeScript engine (02 §2): no DOM, React, Dexie or Node built-ins, no `Math.random` and no `Date.now`. Randomness comes from the seeded RNG, and time is passed in as a parameter. `pnpm lint` (`scripts/check-boundaries.mjs`) enforces this. It runs in the web app, the API and tests.

E01 (#7) delivers the item core: the RNG, the generator registry, item generation and difficulty targeting, response checking, misconception matching, hint ladders, the state models and widget schemas of the 11 fixture formats, and the hooks `tools/content-check` uses. E02 (#10) adds the learner model and its fold in `src/learner`, the projections in `src/folds` and the dashboard signals in `src/signals`; E03 (#16) adds the session planner and `targetDifficulty` in `src/planner`.

Source of truth: `docs/spec/02-architecture.md` §5.2 and §7, and `docs/spec/03-curriculum.md` §5–§7 and §9.

## Two entries (02 §6a)

- `@number-island/engine/shell` (`src/shell.ts`): the skill graph builder, the folds, the learner model, the signals, the RNG and the parameters. It imports nothing of the item core, so an app can put it in its initial JS.
- `@number-island/engine` (`src/index.ts`): everything. Loading it installs the item core (`src/items/install.ts`) behind the port in `src/item-core.ts`.

The learner model reads item difficulty and answer kinds through that port. Until the full entry is loaded, `createEloFireModel`, `learnerModelFor` and `foldLearnerState` throw `ItemCoreNotLoadedError`. An app shell imports the shell entry statically and loads the full entry with `await import('@number-island/engine')` before it folds learner state (`apps/web/src/app/boot/itemCore.ts`). Node code, tests in other packages and lazily loaded modules import the full entry as before. Unit tests in this package import modules by relative path, so `test/setup-item-core.ts` installs the item core for them.

Keep the boundary when you add code: nothing under `src/learner/`, `src/folds/`, `src/signals/`, `src/rng.ts` or `src/params.ts` may import from `src/generators/`, `src/check/`, `src/misconceptions/`, `src/formats/`, `src/strategies/`, `src/items/`, `src/planner/`, `src/placement/` or `src/content/`, not even for a type together with a value (`import type` is fine). `test/shell-boundary.test.ts` and `pnpm bundle-size` check it.

## API

```ts
import {
  initContent, generateItem, checkResponse, detectProcessMisconceptions,
  itemKey, itemSolution, itemExampleCorrect, replaySteps, formatModel, render,
} from '@number-island/engine';

// 1. Bind the compiled content once at startup (web app, API, tests).
initContent({ templates, narration, misconceptions, templateStats }); // packages/content/dist/*.json

// 2. Generate. Same (template, seed, target) → deep-equal item on every device.
const item = generateItem(template, seed);                   // untargeted
const near = generateItem(template, seed, { difficulty: d }); // 24 candidates, closest to d* (04 §2.4)

// 3. Check. Pure; partialCredit is 1 or 0 (the TaskRunner applies hint credit).
const result = checkResponse(item, response);  // { correct, partialCredit, misconceptionIds, feedback, closeness? }
const process = detectProcessMisconceptions(item, response, { latencyMs, trace }); // may tag correct answers
const praise = detectStrategies(item, response, { latencyMs, trace }); // StrategyId[]; correct answers only

// Repeats, lessons and demo mode
itemKey(item);                        // templateId + ':' + canonical params
const steps = itemSolution(item);     // LessonStep[]: hint level 5 and auto lessons
replaySteps(item, steps);             // the response the widget would submit after the steps
formatModel(item.widget.format);      // { configSchema, initialState, apply, toResponse, features }
```

## Adding a generator (03 §10.2)

1. Create `src/generators/<family>/<name>.ts` that exports a `GeneratorDef` (`src/generators/types.ts`). It needs:
   - `params`: every param it accepts, with a type, a default `ParamSpec` and a doc line. Use the canonical names of 03 §5.6 (`a`, `b`, `op`, `unknown`, `result`, …), because misconception rules read them.
   - `derived`: the names constraints may use besides the params (e.g. `result`).
   - `features`: the math features with default weights and docs. Every feature is 0 for the easiest item.
   - `narration`: every `gen.<id>.<step>` key its solutions say. Add each line to `packages/content/narration/common.yaml`.
   - `sample(spec, rng)`: use `sampleAll` from `common.ts`, and enforce families by drawing *within* the template's domains, never by overriding them.
   - `derive(p)` and optionally `accepts(p, t)` for validity the template's constraints don't express (rejected draws are drawn again).
   - `build(ctx)`: one branch per format. Return through `finish()`, which adds the format features and builds the hint ladder from your `solution`. Draw layout randomness only from `rng.fork(...)`, so it never changes the math. Fill `vars` with `pickVars(template, pool)`, so only the slots the lines use reach the UI.
   - `exampleCorrect(out)`: a correct response built directly, not by replaying the solution.
   - `solution(out)`: `LessonStep[]` whose actions, replayed through the format's state model, produce a correct response. The final step enters the answer.
   - `sampleToward` when the parameter space is large or lumpy (03 §5.4).
2. Register it with one line in `src/generators/index.ts`.
3. Add its row to 03 §5.6 in the same PR.
4. Add unit tests (fixed params → answer, widget and solution per format; feature values at the extremes). `test/fixture.property.test.ts` and `pnpm content:validate` (V15) run the 03 §9.4 property test on every template that uses it.
5. Add any misconception rules it needs in `src/misconceptions/rules/`, registered in `src/misconceptions/index.ts`, with tests that include non-discriminating items (`predict` returns `null` when the buggy answer equals the correct one).

## Adding a format model (U03–U05)

Create `src/formats/<format>.ts` exporting a `FormatModel`: `configSchema` (the shared `WidgetConfig` schema plus the semantic rules the widget relies on), `features` and `featureValues` (03 §5.5), and the pure `initialState`, `apply` and `toResponse`. Support every demo op the format lists in `FORMAT_SUPPORT[format].ops`, plus the generic `answer` op (`{ value }`, `{ values }` or `{ id }`), which enters the final answer the way the widget's answer control does. Register it with one line in `src/formats/index.ts`. Add each state checker the format needs in `src/check/state/<id>.ts`, with table tests that include at least one alternative valid end state and the checker's near-miss `exempt` rule.

## Conventions the fixture formats fix (E01)

- **Trace targets.** Countable objects are `obj-<i>` (reading order). Addend counters are `counter-<i>`: `0 … a − 1` for the first addend, then the second.
- **Numeric pick options** use ids `opt-<n>`, so a pick reads back as a number.
- **make-set** responds with `{ count, removed, parts?, bundles? }`. Removed objects wait in a pile beside the container, and dragging takes from that pile first, so a child can put objects back. `removed` is the pile's current size. `parts` is `[left hand, right hand]` for the `hands` container and `[in the container, in the pile]` for `take-away`, which is how a two-part split is shown.
- **tenframe-fill** responds with `{ cells, value? }`, where each cell is 0 (empty), 1 (colour a) or 2 (colour b). A split is shown on two frames, one part per frame (as the authored CPS.02 lesson does); on a single frame the two colours are the parts. `fill` answers on the hundred chart follow reading order.
- **number-bond** split and new-way respond with `{ parts }`. `rekenrek` responds with `{ rows, value? }`, and `number-line-jump` with `{ jumps, value? }`.
- `bond.split` and `bond.newWay` read the two parts from any of these shapes.

## Conventions the geo generators fix (K01)

The shape-sort, shape-compose and compare format models belong to U03–U05; until they land, the property test checks these widgets against the shared schema and skips the solution replay. The puzzle-grid model landed with U04 (#86), so puzzle-grid items now replay their solutions too. The response shapes the K01 checkers read:

- **shape-sort** cards have ids `c0`, `c1`, … in display order. `sort` responds `{ bins: Record<binId, cardId[]> }` (a card in no bin is in the tray; `sort.byRule`). `find-all` responds `{ ids }` (`select.exactSet`, which also still takes numeric `{ values }`). `odd-one-out` answers `choice` with a card id. Demo ops: `drag-card {id, bin}` (no `bin` in find-all: select the card), `highlight-attribute {id, prop}`, generic `answer {id}`.
- **compare** answers `left`, `right` or `same`; demo ops `highlight {side}`, then `answer {id}`.
- **shape-compose fill-outline** (`compose.fill`): pieces and outlines use `src/check/state/pieces.ts` (x right, y up, one unit = one block side). A placed piece is `{ kind, at: [x, y], rot }`: its canonical corners, corner 0 at the origin, turned `rot` degrees counterclockwise, then moved so corner 0 is at `at`. Response `{ pieces: placed[] }`; widget piece ids are `p-<kind>`; demo op `drag-piece {id, to, rot}`. Outlines are `src/generators/geo/outlines.ts` (mirrored in `packages/content/outlines.yaml`). Coverage is the exact area of the union of the pieces inside the outline (`unionInside`: inclusion–exclusion over every subset of overlapping pieces, so three-way overlaps count correctly), not the sum of piece areas. Numeral-pick only draws outlines that its target card (the named kind at `resultScale`) is exactly (`drawsAsCard` in `generators/geo/compose.ts`). Fill-outline is the same config at the concrete and pictorial tiers (GEO.10–11.t4 are pictorial, 02 §5.9 K1).
- **shape-compose place-relative** (`compose.relative`): scene units 100 × 60, x right, y down; anchor sizes are `ANCHOR_SIZE` in `src/generators/geo/position.ts`. Response `{ at: [x, y], layer?: 'front' | 'back' }`; demo ops `highlight-region {relation}`, `drag-piece {id: item, to, rot, layer}`.
- **shape-compose draw-on-grid / build-sticks** (`grid.polygon`): response `{ points: [x, y][] }`, the corners in drawing order on integer dots (in build-sticks, where the sticks meet). Demo op `draw-edge {from, to}` (in build-sticks it lays a stick).
- **puzzle-grid shape-fill** (`puzzle.satisfies`): response `{ fill: string[][] }`; demo op `fill {r, c, value}`. The number variants (`number-path`, `sum-triangle`, `all-ways`) are under "Pattern and puzzle formats" below.

## Conventions K01 fixes for its generators' formats (U03–U05 own the models)

- **measure-length** `iterate` responds with `{ units, value }`: `units` lists where each laid unit starts, in unit lengths from the object's start (any order); `value` is the typed count. `units.iterate` accepts drift up to `gapTolerance` (0.1 unit) per unit, and the last unit must end within `gapTolerance` of the object's end. Solutions use `lay-unit {index}` (plus `unit` in `two-units`), `count-units`, `align-zero`, `read-end` and end with `answer`. Non-standard units are drawn to scale: cube 1, shell 2, stick 4 (`NONSTANDARD_UNIT_SIZE` in `generators/mea/length.ts`).
- **compare-length** objects have ids `obj-<i>` in display order; `longer`, `shorter` and `indirect` answer with that id.
- **compare** and **balance** `which-heavier` answer `left`, `right` or `same`. `mea.length` draws a length compare (the `ruler` representation) as two number-line strips from 0 on one scale, with the object's end marked.
- **order** picture items (`mea.length` with the `ruler` representation, `mea.massvolume`) carry a `stimulus` and no `label`: ruler strips on one scale, or one object picture each. Item ids are `obj-<i>` in display order and `value` is the length or weight step, so the response is still the values in slot order. Their solutions start with a line that places nothing (the worked-step hint plays it), then `drag {id, slot}` per slot.
- **shape-sort** `sort` with object cards (`mea.massvolume`): each card's props are `{ weight }` (the step), bins `b0` (`word.heavier`, `weight >= value + 1`) and `b1` (`word.lighter`, `weight <= value - 1`); `sort.byRule` as for the geo sorts.
- **Weight pictures** (`mea.massvolume` order and shape-sort) carry no numeral, so they only ask comparisons in `CLEARLY_LIGHTER` (`generators/mea/massvolume.ts`): every pair in an order row, and every sort card against the object it is sorted by. Neighbouring steps such as a rock and a melon are never asked.
- **number-pad** (`count.ordinal` `ask: after`): the ordinal `after` pad shows no stimulus. It has blank `n` and ends with `type {blank: n, value}`.
- Solution steps before the last never highlight the answer: the worked-step hint (level 4) plays them.
- **compare** groups (`compare.sets`): left is `a`, right is `b`. On a conflict item one side is an `objects` set with `sizeVaries: true` and `layout: line` (bigger objects spread along the whole side) and the other `layout: array` with two rows (bunched); MC.perceptual-size reads `sizeVaries`. The dots representation is an `objects` set with the `dot` sprite, so the same cue works (the art kit needs a plain `dot` sprite). The concrete tier allows match lines; solutions use `match {left, right}` for the first pair, then `answer {id}`. Symbol items end with `place-symbol {symbol}`.
- **number-line pictures** (a `number-line` stimulus: numberline.place numeral-pick, number-pad and order, estimate.quantity option lines, compare.numbers cards) label both ends: a line with no labels between gets `labelsEvery` max − min (`linePicture` / `pictureLabelsEvery` in `generators/numberline/line.ts`), because NumberLineView labels only multiples of `labelsEvery` and nothing for null. numberline.place rejects bare picture lines whose `min` is not a multiple of the range.
- **number-line-place**: `labelsEvery: null` labels only the two ends; `ticksEvery: null` draws no ticks. `read` shows the target as a marked tick. In `place` mode `benchmarks` (compare.numbers) are labelled reference marks to place the target among; in `closer` mode they are the two choices `b0`, `b1`. Solutions use `zoom {from, to}`, `show-tick {at}` and end with `drop {at}` (or `answer`).
- **numeral-pick** options may carry a `number-line` stimulus with an arrow and no label (numberline.place with the `symbols` representation, estimate.quantity with `number-line`): the child picks the line, and the id is still `opt-<value>`.
- **order** cards that picture a quantity (frames, base-ten, objects, dots: `compare.numbers`, and the `compare.sets` groups) have no `label`, since a numeral would give the order away; path and line cards keep it. On a `compare.sets` conflict order item the fewest group is the `sizeVaries` line, the most the two-row array and the middle one a plain line; MC.perceptual-size predicts the order by those looks. Solutions drag each card into its slot (`drag {id, slot}`).
- **Typed estimates** answer `number` with a `tolerance`: estimate.quantity number-pad within 25% of n (as dot-flash), numberline.place number-pad on a line with no ticks within 10% of the line (`READ_ESTIMATE_PCT`, `readTolerance`), with the target at least that far from both ends so no accepted answer is off the line. The estimate pad is three digits wide for every n.
- **numeral-pick** estimate options (estimate.quantity) are always the rungs of `ESTIMATE_LADDER` (20, 50, 100), shuffled, so the options alone never name the answer. A numeral-pick n lies within 20% of one rung (`estimateRung`), which is the answer; every other option is at least 25% away from n, so the closest option is never in doubt.
- **make-set** (`compare.sets`) makes two groups the same: the boat starts with `a` (`add-more` or `take-away`) and the target `b` is named in the prompt, because MakeSetConfig has no second group to show.
- **base-ten-build** (`pv.number`) follows the U04 model and conventions below: `build` answers `baseten.value { value }` and `build-exact` `baseten.exact { value, exact }` (the canonical counts, or the regrouped ones with `nonCanonical`), with the mat `{ thousands, hundreds, tens, ones }` as the response. A `nonCanonical` `build` sets the tray `limits` one piece short at the lowest non-zero place and to none below it (34: 3 ones; 340: 3 tens, no ones), so no tray-only mat is worth the value and the child must split a piece (`forcedTrade`); the checker takes any mat worth the value. Solutions use `add-piece {kind, count}` per kind (largest first) and end with `count-by {kind}`; a forced trade takes one more piece of the next place up, then `split {kind}` and `add-piece {kind, count: −k}` (puts k back); `read` counts by each kind and ends with `answer {value}`.
- **expanded-form** (`pv.number`): `build` answers the chosen cards (unordered numbers, the non-zero place values; `cards` adds the digits in the wrong places, 1 and 40 for 14), `to-standard`, `fill`, `words` (the widget speaks the target's name; the child types the numeral) and `digit-value` answer a number. `digitIndex` and `highlight-digit {index}` count from the left (U04), while pv.number's `place` counts from the ones. Solutions use `place-card {value}`, `stack-cards`, `highlight-digit {index}` and end with `stack-cards` or `answer {value}`.
- **numeral-pick** words options (`pv.number`) carry `speak: num.<n>` and no label: the widget shows and speaks the number name, and the id is still `opt-<n>`. The options are n's name class (`nameClass`): the digit pairs {p < q} of 1 … `digitMax`, listed in order and paired off two at a time, give classes of two reversal pairs (12, 21, 13, 31), so the set is the same whichever member is the key, every option is a possible key, and each option's reversal is offered. `teen`, `ones.over5` and `tens.over5` are read from the class.
- **MC.teen-reversal** reads these as asking for the number itself: the typed total after filling frames or sliding beads (`thenAsk`, `target.value`), the value of a base-ten build, and the number place-value cards make. Its prediction is the right build with the reversed total typed, the pieces of the reversed number, or its cards.
- **addsub.facts** (K01): a make-ten tenframe-fill starts with `a` colour-a counters in frame 0 and `b` colour-b counters in frame 1 and asks for the total (`tenframe.makeTen`); a make-ten rekenrek starts with `a` on the top row and `b` below, and a plus9 rekenrek puts the other addend (at most 10) on the bottom row; a fact whose preset would not fit two rows of ten is not a rekenrek item. Counting up to subtract is a `number-line-jump` with `goal: difference` from `b` to `a`, answering `{ jumps, value }` with the total jump; MC.count-start-number tags it only when the path lands on `a` and the typed total is one too many. The open number line (and `jumps: free`) allows hops of 1–10 in the item's direction; its near-double solution (`b = a + 1`) jumps `a` again to the double and then 1, the jumps `strategy.used-doubles` praises. **MC.forgot-the-ten** and **MC.wrong-operation** read the asked number the same way as MC.teen-reversal (`rules/asked.ts`): a built item predicts the right build with the wrong number typed.
- **pv.tenmore** (K01): `result` = n + delta · moves + ones. The prompt var `dir` is `more` or `less` (a word slot).
  - **hundred-chart** `move`: `from: n`, `hidden: []`, and `moves` is `moves`× `down` (or `up`), then |ones|× `right` (or `left`); it answers the landing number. The ones never wrap a row (row(x) = floor((x − first) / 10)), and the chart is count.sequence's `chartFor`. The solution is `highlight-col {n}`, one `slide {dir}` per move, then `tap {n}`.

  - **base-ten-build** `build-exact`: `prebuilt` is the `from` pieces and `exact` the `to` counts (`baseten.exact`); bundling only (every trade fuses; unbundling is base-ten-trade). The tray (`tradeLimits`) holds any number of the kind the trades use up and none of any other kind, so a ten is made only by `fuse` (putting ten ones back and taking a rod does nothing to the tens) and a learner who puts pieces back can always finish: pieces of the used-up kind are taken again, and any other piece is rebuilt by trading (a returned rod is ten ones taken and fused). The solution uses `fuse {kind}` and ends with `count-by`.
  - **number-pad** answers n: ten-frames are `{ frames: 2, filled: [10, n − 10] }` (a canonical teen or 20), base-ten and bundles picture the `from` pieces, and symbols show no stimulus (the prompt names the counts; the level-3 hint shows the pieces).

- **mda.addsub** (K01), six formats:
  - **base-ten-build** `build`: `a` is prebuilt as canonical pieces and the target is the result (`baseten.value`); the solution puts in, or takes away (`add-piece` with negative counts), `b`'s tens and ones, then `count-by`. Only items with no carry or borrow.

Adding: `combine {column}` from the ones up, with `trade {from: ones, to: tens}` (and tens to hundreds) when a column reaches ten. Subtracting: `trade {from: tens, to: ones}` when the ones are short (a hundred first when the tens are empty), then `take {column, count}`. A negative count puts pieces taken from that column back on the mat (at most as many as were taken; counts are whole numbers within ±99, anything else is ignored), so one take too many can be undone. The solution ends with `answer {value}`.
  - **number-line-jump**: the open line from `a`, hops of 1–10 in the item's direction, `thenAsk: landing`, `jumps.reach { start, target, allowedJumps, value: result }`; any path is accepted. `tens-ones` (and `none`) hops ten per ten of `b`, then the ones in one hop; `next-ten` hops first to the next ten (subtracting, the previous one), then the rest (37 + 5: 3, 2).

- **bond.parts** base-ten-build and hundred-chart (CPS.09, part unknown): the known part is prebuilt and the target is the whole (`baseten.value`; a tens bond offers rods only, so 100 is ten tens), or the child taps the missing part on a 1–100 chart (the nudge highlights the tens column, never the part's cell). A bond of tens is pictured on the level-3 ten-frame as the bond of its tens (30 and 70 as 3 and 7).
- **count.sequence** `tens` (CNT.20): the first `tens` steps are tens and the rest ones, on number-pad only; the base-ten representation pictures the start, and the prompt var `tens` says how many tens steps come first.
- **count.set** `groupsOf: 10` draws a `groups` layout in tens (34 as 10, 10, 10, 4), and a make-set container holds 10, 20, or the set rounded up to a ten.

MC.place-swap predicts the reversed two-digit number (priority 45, below MC.teen-reversal on 41 → 14). ### Equality and story problems (K01: equality.eq, story.addsub, addsub.three)

The balance and story-problem models (U04, #13) follow these conventions, so the property test replays these solutions too; compare's model is U03's (#12). The response shapes and checkers K01 fixes:

- **balance** terms are numerals `{ n }` at the pictorial tier and objects `{ object, count }` (one unit each, `objectWeights`) at the concrete tier; operations are `{ op }` and the blank is `{ blank: 'x' }`.
  - `fill-blank` answers `number` (the blank). `judge` answers `true` | `false`: the blank shows the right number, or one off by `off` when `truth` is false. `which-heavier` answers `left` | `right` | `same`.
  - `make-equal` responds `{ left, right }`: the unit blocks (or objects) the child added to each pan. The checker `balance.equal` `{ left, right }` holds what each pan already weighs, and accepts any blocks that make the pans level (adding to both pans is an alternative). equality.eq leaves the blank off the right pan (`a + b = c + _`: the right pan holds `c`); compare.sets puts `a` and `b` objects on the pans (`ask: make`). The tilt shows at the concrete tier (compare.sets) or always (equality.eq). Pan values and added counts are whole, non-negative and at most `MAX_BLOCKS` (1000), so a float sum past 2^53 can never round two unequal pans level. The property test's near misses add or remove one block on a pan; the hint check treats the blocks the light pan needs as the answer.
  - Demo ops: `highlight-side {side}`, `place {side, term, count?}` (puts `count` copies of the term on the pan; on a `fill-blank` pan it fills the blank), `level`, `tilt`, and the generic `answer {value}` or `{id}`. Solutions end with `place` (make-equal) or `answer`.
- **compare** `true-false` (equality.eq) puts the whole statement on the left as an `expression` (`3 + 4 = 5 + 2`) with the right side `none`; it answers `true` | `false`. `same-or-not` (compare.sets `ask: same`, ALG.05) answers `same` | `not-same`. Both are answer sets the format fixes at two (03 §9.4 step 9).
- **story-problem** (`story.addsub`): `lines` are the story in telling order, `p.story.*` keys with their own vars; the last line asks the question. `{who|name}` is `@resident` (03 §4.6), `{item}` and `{other}` are contexts.yaml nouns, and `{many}` is 2, so a noun slot counted by `many` is plural. Each context speaks its own verbs (`p.story.<context>.*`); `generators/story/contexts.ts` mirrors the contexts it uses, and `test/story-contexts.test.ts` keeps it in step with contexts.yaml. The scene shows only the told quantities. One blank `x` answers `number`; `put-together/both` has blanks `x` and `y` and responds `{ parts: [x, y] }`, checked by `bond.split { whole, nonZero: true }` (any split); it tells only the whole `a`, so `b` is ignored (read as 0, sampled at its least value) and its hint picture is the bar of the whole with two unknown parts. Solutions use `highlight-line {index}`, `act-out {sprite, count}` or `show-scene`, and end with `answer {value}` (or `{ values }`).
- **number-pad** stories (`story.addsub`) carry the story in the template's prompt, so such a template fixes its situation and context. `ask: equation` shows `a op _ = _` with blanks `y` and `z`, answered `numbers [b, result]` (ordered).
- **numeral-pick** equations (`story.addsub`, ADD.23): option ids `eq-<x>-plus-<y>` / `eq-<x>-minus-<y>`, a `label` such as `5 + 2 = 7`, and `speak` `p.story.eq-plus` / `p.story.eq-minus` with vars `x`, `y`, `z`. The four options are the 2 × 2 grid x0 or x0 + 1 with y0 or y0 + 1, all true equations of one operation; the param `corner` (0–3, which the template draws) is the told equation's cell, so for every option set each option is the key of some draw and only the picture or story tells them apart. Every option number is 1 to `maxTold` (the template's a and b domains), and an addition grid never has x0 = y0, which would offer x + y beside y + x.
- **tenframe-fill** with three addends (`addsub.three`): `a` is prefilled in frame 0 and the config's `b` is b + c; the solution puts in a's ten partner first (or b and c together into frame 1 when they make ten), then counts (`tenframe.total` with the typed total). MC.count-all-instead counts `a + b + c` counters.
- **MC.equals-means-answer** predicts a op b on a two-sided fill-blank, the left side's answer added to the right pan on a two-sided make-equal, and `false` for a true judged equation that is not `a + b = c` (`_ = a + b`, or operations on both sides). **MC.equals-add-all** predicts the sum of the numbers shown. **MC.start-unknown-reversed** reads the two shown numbers of `_ op b = c` (equality.eq), `unknown: start` (addsub.facts) and the start-unknown stories. **MC.keyword-more-means-add** predicts a + b on the comparing stories whose answer is a − b. These two rules `apply` only to the items they read (start-unknown items; comparing or inconsistent-language stories), so V25 counts only those. **MC.symbol-reversed** predicts the mirror of `<` or `>` on a `symbol` compare.

### Sharing and fraction formats (K01: div.share, frac.partition, frac.compare; fraction-cut, fraction-pick and fraction-line have no model yet)

- **fraction-cut** (`fraction.cut { parts, shade, acceptNonCongruent }`) responds with `{ regions: number[], shaded: number[] }`: each cut region's share of the whole area (any order, summing to 1) and the indices of the shaded regions. Each region must be within 3% of the whole area of 1/parts (`FRACTION_AREA_TOLERANCE`), and any `shade` distinct regions may be shaded (the checker exempts shading another part). The response holds areas only, so `acceptNonCongruent` is a widget rule (guided cuts are congruent). `thenName` adds `name: [shade, parts]`. Solutions use `cut {line}` (guided lines numbered from 0, `cutLines` in `generators/frac/partition.ts`: a circle's diameters, a rectangle's cross for fourths, parallel lines on a strip, numbered left to right), then `shade {part}`. Halves and fourths cut the middle first (`cut-middle`), as the h.frac.cut-middle hint says: a strip into fourths cuts line 1, then line 0 and line 2, one half each (PR #84 review round 2).
- **fraction-line** `partition` (`fraction.partition { denominator, max }`) responds with `{ cuts: number[] }`: the marks placed, in units from 0 (any order, 0 < x < max). A mark on a whole inside the strip (1 … max − 1, within the same 2%) is ignored; the others must match k/denominator (not wholes) one to one within 2% of the unit (`PARTITION_TOLERANCE`). A mark next to an end of the strip is not ignored: it cuts off a sliver, so it counts as an extra mark (PR #84 review). Solutions name the middle first and end with `partition {b}`.
- **fraction-pick** `fair-or-not` answers `yes` | `no` about its `stimulus` and has no `options` (a fixed pair, like equal-share). `pick-picture` options are `fraction` pictures with ids `pic-<k>` in display order and no label. frac.partition's pick items show one shape three ways (halves, fourths, and `unequalParts` parts that are not equal, a param of its own so the set never depends on the key; the set's `denominator` feature is 2) and the prompt names one with a word clip (`word.halves`, `word.fourths`, `word.unequal-parts`), so every picture is the answer of some item. Solutions say what to look at (no action), then `answer {id}`.
- **equal-share** (div.share): `fair-or-not` and `fix` pre-deal each ± `shift` to two plates (the rest get each); `fix` asks `each` on that pre-dealt share, so the child takes back from the bigger plate (`deal {to, count: −shift}`) and gives to the smaller one. `each` solutions `deal-round` once per item each gets, then `set-aside-leftover`, and end with `answer {value}`. The number-pad `moves` item pictures the pair as an `objects` set with `layout: groups`.
- **compare** and **order** (frac.compare) show `fraction` pictures with one part shaded. Order values are the piece size in 24ths of the whole (24 ÷ den: 2 → 12, 8 → 3), direction `desc`, so the answer is biggest piece first; the order model's `magnitude` is 0 for them. With the `symbols` representation (FRA.08's abstract tier) an order card has no picture and is labelled with its part count (`"<den>"`), so the child orders by "more parts, smaller pieces" alone. FRA.08 has no fraction-cut template: cutting one shape compares nothing, so all its constructed practice orders pieces of wholes cut differently (PR #84 review round 2).
- **MC.fraction-unequal-parts** predicts `yes` on an unfair fair-or-not item, the unequal picture with as many parts on a halves or fourths pick, a cut moving half a part from the first region to the second (`unequalRegions`), a partition with the first mark moved 0.4 of a part (`unequalCuts`), the pre-dealt share left as it is on `fix`, and 0 on `moves`; it matches every cut or partition with the right count that is not even. **MC.fraction-bigger-denominator** predicts the side cut into more parts, or the order reversed. **MC.unequal-share** has no prediction: it matches a `share.fair` response with unequal shares, or a leftover that could go round again.

### Data formats (K01: data.sort, data.chart; the bar-graph-read and bar-graph-build models are U05's, see "Patterns and data models")

- **Charts** (`ChartSpec`) use scale 1 and two or three categories. Category ids are the island object (noun) ids (`fish`, `crab`, `shell`, `firefly`: art-kit sprites, so every chart and sort draws; shared things are `shell`, `fish`, `crab`, `pebble`) and labels `noun.<id>.many`. Picture graphs, tally charts and tables are horizontal, bar graphs vertical; `axisMax` is at least 5.
- **bar-graph-read** answers `number` for `how-many` (the one category in `question.categories`), `total` (every category) and `difference` (first − second of `question.categories`, always positive), and `choice` with a category id for `most` and `least`, whose `question.categories` lists every category. A most or least item never has a tie, and the chart's categories are its options (the property test needs two or more). Solutions use `count-pictures {id}` (picture graphs, tally charts, tables) or `read-axis {id}` (bar graphs) per category, then `answer`.
- **bar-graph-build** shows `data` (`objects` to tally first, `tally` marks or a `table` of counts; `data.values` in chart category order) and an empty chart: its categories carry value 0, so the widget never shows the counts it asks for. The response is `{ values }`, the count the child built for each category in chart order, whatever the marks are (bars, pictures or tally marks), and `chart.values { values }` checks it exactly. Solutions use `tally {id, count}`, `add-picture {id, count}` or `raise-bar {id, to}` per category. The property test's near misses add or take away one mark in one category.
- **compare** (data.chart): two one-bar charts on one scale (category a and category b, sides shuffled); `ask` `more` or `fewer`, and equal counts answer `same`.
- **number-pad** (data.chart) shows a picture graph (`kind: picture` only) as a `scene` stimulus, one group of pictures per category, because StimulusView draws no `chart` (PR #84 review), and asks for the total or the difference. StimulusView wraps the groups, so two can share a line: its hints talk about groups, never rows; (data.sort) an `objects` picture of one kind among `distractors` of another, counting the asked kind.
- **shape-sort** sorts (data.sort): object cards carry props `{ kind }` with bins `noun.<kind>.many`; shape cards carry `{ shape, color, size }`, sorted by colour (`word.red`, `word.blue`, `word.yellow`), shape (`shape.<kind>.many`) or size (`word.big`, `word.small`, scale 1.5 or 0.6). Response `{ bins }` (`sort.byRule`, as for the geo sorts). A sort shows no count or order, so it is DAT.01 practice only: DAT.10 (count each group and order the groups) has no shape-sort template (PR #84 review round 2).
- **order** (data.sort): one objects picture per group, no label, put in order from the fewest; values are the counts, which are all different.

### Time formats (K01: time.clock, time.sequence; clock-set and clock-read have no model yet)

- **clock-set** answers state `clock.time { h, m }`. The response is `{ h, m }`, the time the geared hands show: `h` the hour the short hand has reached (1–12), `m` the minute the long hand points at (0–59). The checker compares face times, so any `h` for the same hour on the face counts (12 and 0, 3 and 15); a minute outside 0–59 is not a reading. K01 items start at `start` 12:00 with `precision` 5, so a swapped setting (12:15 for 3:00) can be made. Solutions use `highlight-hand {hand: 'minute'}`, `drag-minute {to: m}`, `highlight-hand {hand: 'hour'}` and end with `drag-hour {to: h}` (the hour hand then sits between `h` and the next hour by `m`). The property test's near misses move the short hand one hour or the long hand five minutes.
- **clock-read** `digital-pad` answers `numbers` `[h, m]`, ordered, with `h` 1–12. `pick` (K01: TIM.09, `ask: hour`) asks only which hour it is after: the options are hours with the numeric pick ids `opt-<h>` and labels `"<h>"`, the run of consecutive hours the hour is in, from a fixed partition of the face (`hourClass`: 1–4, 5–8, 9–12 with diagnostic distractors, otherwise runs of three). Every hour of a run gets the same options and is the key of some item, so the options never give the hour away (PR #84 review); MC.hour-hand-next and MC.hour-minute-swap predict an option only when it is in the run. Solutions use `point-hour`, `point-minute` and end with `answer {values}` or `answer {id}`.
- **Clock features**: time.clock emits the 03 §5.5 clock format features itself. The precision features read the target time (the finest step it needs: half, quarter, five or one minute), not the widget's snapping, and the hour pick reads no minutes, so it has none. `turn` is how far the hands travel from the start, the shorter way round (half a day = 1).
- **MC.hour-minute-swap** and **MC.hour-hand-next** read a buggy face time and answer with the item's own kind (`rules/clock.ts`): numbers `[h, m]` on the pad, the state `{ h, m }` on a clock-set (null when the long hand cannot reach the minute), the `opt-<h>` option on the hour pick. - **order** (time.sequence): one objects picture per daily event (sprite `event-<id>`: wake-up, breakfast, lunch, dinner, bedtime), no label; values are the event's place in the day (1–5), `direction: asc`. On the timeline template one event is pre-placed through `fixed` on its own slot. Solutions start with a line that places nothing, then `drag {id, slot}` for every slot that is not fixed.
- **shape-sort** `sort` (time.sequence): `event` cards (no `isPm`, which would show the bin), target props `{ part: 'morning' | 'night' }`, bins `b0` (`word.morning`) and `b1` (`word.night`); `sort.byRule`. Solutions `drag-card {id, bin}`.

### Pattern and puzzle formats (K01: pattern.repeat, pattern.grow, puzzle.grid; pattern-extend's model is U05's, see "Patterns and data models"; puzzle-grid's is U04's, see below)

- **pattern-extend** `extend` and `fill` answer state `pattern.tokens { expected }`: the response is `{ tokens }`, the tokens placed in the blanks (the `null` entries of `sequence`) in reading order, each the same unit as expected (`{ sprite, color? }`, `{ n }` or `{ tiles }`, every field equal). `fill` hides the tokens ending one before the last, after at least one whole core. `core` answers `select.exactSet { values }`: the indices of the first repeat of the core (the prompt asks to mark it from the start). `rule` answers `number`, the step. `palette` holds the units a repeating pattern uses (A, B, C order) and is empty for number patterns, which are typed. Solutions use `place-token {index, token}` per blank, or `highlight {index}` and `bracket-core {from, to}`, after a first line that places nothing. The property test's near misses take away the last token or swap one for its neighbour.
- **Pattern units** (pattern.repeat) come from the params: `theme` picks three units from `OBJECT_THEMES` (island sprites) or, with the `shapes` representation, `SHAPE_THEMES` (a shape kind as the sprite plus a colour; every unit differs in both). pattern.repeat and pattern.grow emit the pattern-extend format features they use (`core.len`, `hidden.middle`, `step.notOne`) themselves.
- **order** (pattern.repeat): the whole pattern as cards with one-object pictures and no label, values 1, 2, … in pattern order; the first `shown` cards (more than one core) are `fixed` in their slots and the child places the next `ask`, which are always different units, so no two free cards look alike. With `mode: core` (ALG.04.t3, "make the next repeat") the fixed cards are whole cores and the free ones exactly one more core. Solutions start with a line that places nothing, then `drag {id, slot}`. **MC.pattern-restart** (`rules/patternRestart.ts`) predicts the blanks filled from index 0, the free cards placed in the order of the first cards, and on core items the bracket that stops where the first unit comes back (AAB → the first A); it is null when that is the answer, and it does not apply (`applies`) to `mode: core` orders, where starting again is the answer.
- **hundred-chart** `pattern` (pattern.grow): `patternShown: 3` makes the chart shade `patternStart + k·patternStep` for k = 0, 1, 2 as given terms (`patternGiven(config)`; a tap on one changes nothing) and the child taps the next terms; how many is in the prompt (`ask`), and the answer is `select.exactSet { values }`. `hidden` is empty. Solutions highlight a row, then `tap {n}` per term.
- **number-line-jump** (pattern.grow): `goal: add`, `thenAsk: landing`, from the third term, with `allowedJumps` [1, 2, 10] so the jumps never give the rule away; `target` (the next term) is not drawn on an `add` line. The answer is `jumps.reach { start, target, allowedJumps, value }`.
- **puzzle-grid number variants** (`puzzle.satisfies`): target `{ variant, rows, cols, cells, givens, constraints, palette, nonZero? }`, with `cells` every puzzle cell as [r, c] and `givens` the shown numbers as [r, c, value]. The response is `{ fill: (number | '')[][] }` (rows × cols): each puzzle cell a whole number (from `palette` when it is not empty), the givens unchanged, '' elsewhere. `number-path` (PUZ.01) lists `cells` in path order (a snake through the grid) with one `adjacent-step` constraint (step 1): each cell is one more than the one before it. `sum-triangle` (PUZ.02) is a 3 × 5 grid with corners (0, 2), (2, 0), (2, 4) and middles (1, 1), (1, 3), (2, 2), one `line-sum` per side; its blank sets (`BLANKS` in `generators/puzzle/grid.ts`) always solve one side at a time. `all-ways` (CPS.06) has a row of two blank cells for each way to make the whole (both parts non-zero, turn-arounds once), a `line-sum` per row, and the rows must be different ways, so any order and either way round is correct (the checker's near-miss exemption). Demo op `fill {r, c, value}`; the near misses change one number by one. Solutions fill in dependency order (PR #84 review round 2): a sum triangle repeatedly names a side with exactly one empty cell (`check-line {index}`, the side's `line-sum` index) and then fills that cell, so a blank corner is found from its solved side before the side it completes; a number path fills a blank only when a path neighbour is known (counting on from the cell before it, or back from the cell after it). All ways fills row by row.
- **hundred-chart** `fill` (puzzle.grid, PUZ.01): a puzzle piece (`PIECES`) cut out of the 1–100 chart, every cell 1–99; `hidden` is the piece in reading order and the answer its numbers in that order. Solutions highlight a row and end with `answer {values}`.
- **number-bond** (puzzle.grid sum-triangle): one side of a triangle, `missing-part` with the whole the side's sum and the known part the two corners together; the answer is the middle.
- **order** (puzzle.grid all-ways): every way to make the whole as a two-group objects picture (`layout: groups`, turn-arounds included), no label, value = the first group; `direction: asc`.
- **number-bond** `new-way` with `gap` (bond.parts, CPS.06): `found` is every way but one in order (1 + (n − 1), 2 + (n − 2), …), so bond.newWay accepts only the missing way (either way round).

### Balance, story-problem and puzzle-grid models (#13)

- **Balance** follows K01's conventions above:
  - `make-equal` answers the units added to each pan, one per block or object.
  - In `fill-blank`, `place {side, term: {n}}` fills that pan's blank.
  - In `which-heavier` the pans hold the config's terms. MEA.16's worked solution places them again, so a single placement that matches a preloaded term changes nothing. Each preloaded term can be matched once. Any other placement adds to the pan: a repeat, a new term, or a `count` above 1.
  - A placed term (`count` copies, at most `MAX_BLOCKS`) goes on its pan as `+ term`, so the pan keeps a value.
  - A side's value uses × before + and −; objects count as `count × objectWeights[sprite]`.
- **Story-problem:** `situation` is the 03 §5.5 prior itself (weight 1). `extraneous` and `inconsistentLanguage` are 0 from the config alone; the generator sets them, and generator values win.
- **Puzzle-grid** answers `{ fill }`: rows × cols, each puzzle cell's value (given or filled), with `''` outside the puzzle, checked by `puzzle.satisfies` `{ variant, rows, cols, cells, constraints, palette }`. The generic `answer {values}` fills the blanks in reading order.
  - **Numeric variants** (`cage-sum` mini-KenKen 3 × 3 and 4 × 4, `magic-square`, `missing-digit`, `sum-triangle`, `digit-cards`) take the config's own `cells` (`{ r, c, given?, blank?, cage? }`). Given cells keep their values, and every blank holds a number from the target's `palette` (required for these variants). The model's `fill` only takes palette values.
  - **Mini-KenKen** (`cage-sum`) is an n × n grid of the digits 1–n. The schema requires a square grid with a cell at every position, and palette and given values from 1–n. The checker rejects any other value or a missing position, whatever the target's palette says.
  - **Supported constraints:** `cage-sum`, `row-unique`, `col-unique`, `line-sum` and `use-each`. `use-each` covers the blanks, or every cell when it lists one value per cell. `adjacent-step` is accepted for `number-path` only (K01's PUZ.01): each cell, in `cells` order (the path), is `step` more than the one before it. Both target forms check it: K01's `[r, c]` targets (above) and config-cell targets.
  - **Not checked yet:** `equation` and `clue`, and `adjacent-step` on any variant but `number-path`. They fail the `puzzle-grid` schema, and the checker rejects them in both target forms. One rule (`stepHolds`) checks a number path's step in both forms: whole numbers of 0 or more, each `step` more than the one before. For a number path the schema rejects only configs that are structurally ungradable: a non-whole step, or a non-whole or negative given. It does not check the palette, and it does not guarantee that a correct fill exists. Solvability is the generator's job, verified by the 500-seed property test that replays every generated item.
  - **What the schema rejects:** configs that can't be met for structural reasons. That covers:
    - a non-number palette or a non-number given in a number grid;
    - more than one `use-each` list;
    - a numeric `use-each` that isn't palette numbers for the blanks, or the givens plus palette numbers for every cell;
    - a `shape-fill` `use-each` whose pieces aren't in the palette, don't add up to the outline's cells, or need more rectangles than the outline has disjoint side-by-side pairs (a maximum matching). `shape-fill` outline cells must all be blank (as 03 §5.5 and `geo.compose` have them), so the matching sees every cell as free;
    - only `use-each` constraints are allowed for `shape-fill`.
  - **What it doesn't check:** whether the sums and uniqueness rules have a solution. That is the generator's promise. The property test replays each generator's solution through the model and checker (03 §9.4), as it does for `uniqueSolution`.
  - `shape-fill` (K01) keeps its own rules, with `cells` given as `[r, c]`.

### Fractions (fraction-cut, fraction-pick, fraction-line)

The models follow K01's shapes ("Sharing and fraction formats" above). Picture geometry is `src/formats/fraction-geometry.ts`: the fraction-cut model computes its areas from it and the widgets draw exactly those parts, so a picture cannot disagree with its numbers. A rectangle-like whole is the unit box (x right, y down); a circle's parts are sectors in degrees clockwise from 12 o'clock. Parts are numbered in reading order (a circle: clockwise from 12 o'clock).

| Format / mode | Response | Checker / answer | Ops (args) |
|---|---|---|---|
| `fraction-cut` | `{ regions, shaded }` (+ `name: [a, b]` with `thenName`); null until the whole is cut | `fraction.cut { parts, shade, acceptNonCongruent, thenName? }` | `cut {line}` (guided line, from 0); free: `cut {dir: 'v' \| 'h', at}` (rect-like, 0 < at < 1; a grid snaps to cell lines), `cut {angle, through?}` (circle radius or diameter), `cut {dir, at, part}` (inside one part, only with `acceptNonCongruent`); `shade {part, off?}`; `separate`, `stack-parts` (views); `answer {values: [a, b]}` |
| `fraction-pick` `fair-or-not` | `choice` `yes` \| `no` | `choice` | `count-parts`, `highlight {id: 'stimulus'}`, `answer {id}` |
| `fraction-pick` `pick-picture`, `compare`, `equivalent`, `name` + `words` | `choice` option id (pick-picture: `pic-<k>`) | `choice` | `highlight {id}`, `overlay {a, b}`, `answer {id}` |

| `fraction-line` `partition` | `{ cuts }`: marks in units from 0, sorted; null while none | `fraction.partition { denominator, max }` | `drop {at, remove?}`, `partition {b}` (every non-whole k/b) |
| `fraction-line` `place` | `placement`, the value in units | `placement` | `drop {at}`, `hop {k}` (to k/denominator) |
| `fraction-line` `read`, `equivalent` | `numbers` `[a, b]`; `read` with `decimalLabels`: `number` | `numbers` (`equivalentOk` for equivalent) | `answer {values}` or `{value, slot}`; `label {a, b}`, `hop {k}`, `partition {b}` are visual hints here |

- **Taking back.** These are what the child's own touch sends to the model; they are not authored demo ops (`FORMAT_SUPPORT` and the widgets' demo op lists are unchanged, so a worked example cannot use them). Each thing a child does has an op that undoes it where it is: fraction-cut `mend {line}` / `mend {dir, at}` / `mend {angle, through?}` joins the parts along one cut (a joined part is filled only when every piece was; a guided line whose cut is gone can be cut again) and `shade {part, off}` empties a part; fraction-line `drop {at, remove}` takes a mark away and, in `place`, `drop {remove}` takes the point back; fraction-pick `answer {id, off}` takes that pick back.
- **Supported domain** (schema and `apply`, one test per bound in `src/formats/fraction-domain.test.ts`). fraction-cut: 2–12 parts; `shade` 0–`parts`; grids 1–12 cells a side and ≤ 100 cells; never more than 12 parts on screen; a free cut leaves no piece under 1/24 of the side or 15° (finer than any part `fraction.cut` accepts); typed names are whole numbers 0–99. fraction-line: `max` 1–3; `denominator` 1–12; `partition` 2 or more parts a whole and ≤ 6 on the whole line (a pin for every mark, a full target with its gap in the smallest area), never with `ticksShown` or `labels: 'all'` (they are the answer); a target placed on shown ticks has `denominator < 2b` (only its own tick is within the 1/(2b) tolerance, `placeTolerance`); target `b` 1–24 and the target on the line; ≤ 12 marks; typed numbers whole 0–99, a decimal 0–`max`. fraction-pick: 3–4 options (pictures stay big enough to count their parts in the smallest area); exactly 3 options when any card has no picture (word and symbol cards are wide: a fourth scrolls the smallest area in K); pictures 1–12 parts, `shaded` ≤ `parts`; overlay `b` 1–12, `a` ≤ `b`.
- **Placing** (`snapPlacement(config, at)`): a point dropped on a fraction line lands on the nearest tick when ticks are shown (a tie goes to the smaller) and otherwise where it is put, to a millionth; the widget sends the raw place and the model lands it, so the widget and the `placement` checker read one value.
- **Guided lines** (`guidedLines(shape, parts, gridSize)`; their count is `cutLines` in `generators/frac/partition.ts`): a circle's diameters for an even count (line i through i·360/parts and the opposite angle) or radii for an odd one; a rect or square in fourths the cross (line 0 vertical, line 1 horizontal); a grid strips along cell lines (columns if they divide into the parts, else rows); otherwise vertical lines at k/parts. Cutting a line again does nothing; cutting a filled part leaves both pieces filled; a circle with one radius is still whole (a slit).
- **Congruence** is the widget's rule (the response holds areas only): without `acceptNonCongruent` every cut runs the full length, and equal-area parts made that way are congruent; with it, `cut {…, part}` cuts inside one part, so equal areas of different shapes can be made (FRA.14, FRA.16).
- **Schemas.** fraction-cut: 2–12 parts, `shade ≤ parts`, `thenName` needs `shade ≥ 1`, `gridSize` exactly on the grid (≤ 100 cells, sharing evenly into the parts; guided grids need strips). fraction-pick: every mode with options shows ≥ 3 with distinct ids (03 §5.1), pick-picture options are `fraction` pictures, fair-or-not and name have a `stimulus` (fair-or-not a fraction), only `name` has `nameInput`. fraction-line: `partition` has no target and 2+ parts; the other modes have a target on the line, `read`/`equivalent` targets (and `place` targets with ticks shown) sit on a tick, `read` asks for the line's own denominator, `decimalLabels` are tenths, at most 12 parts a whole.
- **Fraction pictures** (`fractionPicture(shape, parts, equalParts)`): equal parts are the guided cut of the whole, exact by construction. Unequal parts use `UNEQUAL_WEIGHTS` (the biggest part ≥ 1.5 times the smallest, so no unequal picture passes for equal): an off-centre cross for a rect in fourths, an off-centre chord for a circle in two, otherwise strips or sectors of different sizes. The first `shaded` parts are filled.
- **Features.** fraction-pick reads only sets and maxima of what it shows (options are shuffled): `denominator` is the largest shown − 2, and `unequalDistractor` an unequal option that is not the answer. fraction-line's `ticks.hidden` is 0 in `partition` (it never shows the ticks it asks for). Where frac.partition emits a feature itself (`denominator`, `parts.hard`, `shape.circle`), its value wins.
